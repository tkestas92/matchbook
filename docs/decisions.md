# Architecture decisions

Short records of important choices: what was decided and why.
New entries go at the bottom. Format: context → decision → consequences.

---

## 001 — Monorepo
**Context:** backend, generator, mock APIs, pipelines, MCP server, evals and frontend are tightly related.
**Decision:** one repository.
**Consequences:** one CI, one set of agent rules, coding agents see the whole system.

## 002 — uv and Python 3.12
**Context:** need reproducible environments; 3.11/3.12 are the most common production versions.
**Decision:** manage dependencies and the Python version with uv; target Python 3.12.
**Consequences:** fast installs, lockfile, no separate pyenv setup.

## 003 — Four database schemas: raw, core, app, eval
**Context:** need to re-normalize without re-fetching, and evals must not leak into the system under test.
**Decision:** `raw` (as received), `core` (normalized), `app` (application state), `eval` (answer key).
**Consequences:** normalization bugs are fixable from `raw`; no module can "find" errors by reading `eval`.

## 004 — Least-privilege database roles
**Context:** an LLM agent will generate SQL.
**Decision:** separate roles `etl`, `app`, `agent_ro`, `eval_runner`; `agent_ro` is SELECT-only on curated views with RLS.
**Consequences:** safety is enforced by the database, not by prompts. A test proves `agent_ro` cannot write or read `eval`.

## 005 — Money as Decimal / NUMERIC(12,2), EUR only
**Context:** reconciliation compares amounts to the cent; floats introduce rounding errors.
**Decision:** `Decimal` in Python, `NUMERIC(12,2)` in PostgreSQL for all billable amounts, single currency EUR. The one exception is internal pipeline cost (decision 014).
**Consequences:** exact comparisons; multi-currency is out of scope.

## 006 — UTC storage, agency timezone for reporting
**Context:** platforms report in different timezones than invoices; month boundaries shift spend.
**Decision:** store UTC; compute reporting dates in `Europe/Vilnius`; keep each platform's timezone in `core.platforms`.
**Consequences:** timezone shifts become detectable and explainable instead of looking like overcharges.

## 007 — Rules first, AI second
**Context:** LLMs are costly, slow and can be wrong; most reconciliation is arithmetic.
**Decision:** deterministic code for everything computable; LLMs only for messy documents, fuzzy name matching, summaries and natural-language questions.
**Consequences:** stage 1 runs with no AI and gives a measurable baseline; AI value is shown as an improvement over it.

## 008 — Pipeline steps are plain functions; Airflow only orchestrates
**Context:** Airflow is heavy to develop and test against.
**Decision:** each step is a plain Python function runnable via `make pipeline`; Airflow DAG just calls them.
**Consequences:** fast unit tests; orchestrator can be swapped.

## 009 — Synthetic data with a planted-error answer key
**Context:** no access to real agency data; need ground truth to measure quality.
**Decision:** deterministic generator creates a true world, renders messy documents, plants errors and records them in `eval.answer_key`. Ratios come from a public Kaggle ad dataset.
**Consequences:** every module gets found / missed / false-alarm metrics. README states clearly that data is synthetic.

## 010 — Single LLM access layer
**Context:** need model switching, fallback, cost tracking and tracing.
**Decision:** all LLM calls go through `backend/app/llm/`.
**Consequences:** one place for provider adapters, retries, cost caps and Langfuse.

## 011 — Public repository, English
**Context:** the project is a portfolio piece for international and Lithuanian employers.
**Decision:** public from day one; code, docs and commits in English.
**Consequences:** commit history shows how the project grew.

## 012 — Schema conventions: TEXT + CHECK enums, run_id without FK, updated_at by trigger
**Context:** the schema will evolve every stage; the pipeline upserts with `INSERT … ON CONFLICT`; `core` and `app` are written by different DB roles.
**Decision:** enum-like columns are `TEXT` with a named `CHECK` (not PG `ENUM`). `run_id` is a `UUID NOT NULL` on every pipeline-written row with **no** FK to `app.pipeline_runs`. `updated_at` is set by a `BEFORE UPDATE` trigger (`core.set_updated_at()`), not by the ORM. `app.audit_log` is insert-only via a trigger that rejects UPDATE, DELETE and TRUNCATE. FKs from financial tables use `ON DELETE RESTRICT`; `eval` has no FKs into `core`/`app`.
**Consequences:** adding an enum value is a one-line migration; `core` does not depend on `app`; upserts keep `updated_at` correct; audit history and financial rows cannot vanish by accident.

## 013 — Ad accounts carry the reporting timezone; IO unique includes start_date
**Context:** Meta and Google report in the *account* timezone (plan §5.3), and a campaign without an IO had no link to a client. The same `campaign_ref` can be reused on a later flight.
**Decision:** add `core.ad_accounts` (client, platform, external account id, timezone); every campaign belongs to an ad account. `core.platforms.timezone` stays as the platform default. `core.insertion_orders` is unique on `(client_id, platform_id, campaign_ref, start_date)`.
**Consequences:** delivery converts from the right timezone per account; every campaign has a client before IO matching; renewals do not collide with prior flights.

## 014 — Pipeline cost uses NUMERIC(12,6)
**Context:** money is `NUMERIC(12,2)` (decision 005), but a single LLM call costs fractions of a cent.
**Decision:** `app.pipeline_runs.cost_eur` is `NUMERIC(12,6)` — the one exception. It is an internal cost metric, never billed.
**Consequences:** per-run cost tracking and cost caps stay accurate; all billable amounts remain `NUMERIC(12,2)`.

## 015 — Login roles via `make roles`, privileges via migrations
**Context:** decision 004 needs roles `etl`, `app`, `agent_ro`, `eval_runner` with passwords from env. Roles are cluster-wide (shared by every database, incl. throwaway test databases); passwords are per-environment secrets that rotate.
**Decision:** `make roles` (`backend/app/db/roles.py`) idempotently creates the login roles and sets `LOGIN`, `PASSWORD` and explicit no-privilege attributes from `.env`; the password is quoted server-side with `format('%L')`. Migration `0002` owns everything database-scoped and non-secret: grants, default privileges, views, RLS, `statement_timeout`. It creates missing roles as `NOLOGIN`, so `make roles` and `make migrate` work in either order. Downgrade revokes but never drops roles.
**Consequences:** no secrets in migration files or `alembic --sql` output; rotating a password is `make roles`; a fresh environment runs `make up && make roles && make migrate`.

## 016 — Agent access: owner-rights views + RLS keyed on `app.user_id`
**Context:** `agent_ro` runs LLM-written SQL. It must read only curated views, never base tables, and only for clients its user may see. `security_invoker` views would require `agent_ro` to have SELECT on base tables; `FORCE ROW LEVEL SECURITY` does not help because the table owner is a superuser and superusers always bypass RLS.
**Decision:**
- A `NOLOGIN` role `agent_views` (not superuser, not table owner) has SELECT on the base tables the views need and **owns** `core.v_spend_daily`, `v_pacing_base`, `v_invoices`, `v_issues` (`security_barrier`). Postgres applies base-table RLS as the view owner, so policies `TO agent_views` fire for every view read. `agent_ro` has only `USAGE` on `core` + `SELECT` on the four views.
- Policies filter by `core.agent_client_ids()`: a `SECURITY DEFINER` function returning the client ids in `app.user_client_scope` for `current_setting('app.user_id', true)`. Unset, empty, unknown or unscoped user → empty array → **zero rows** (fail closed). Other roles get `USING (true)` policies; rows without a client (platform invoices, client-less issues) are hidden from the agent.
- `EXECUTE` on `set_config(text, text, boolean)` is revoked from `PUBLIC` and granted only to `etl`, `app`, `eval_runner`, so a `SELECT set_config('app.user_id', …)` from the agent fails. The trusted caller sets scope with `SET LOCAL app.user_id = …` in the transaction before the agent's query.
- `agent_ro` has `statement_timeout = 5s` in this database; `TEMPORARY` is revoked from `PUBLIC`.
**Consequences:** access rules live in the database and are proven by `test_roles.py`. `SET`/`RESET` are commands, not functions, so the revoke alone cannot stop them: the stage-3 SQL executor **must** accept only a single `SELECT` statement and reject everything else before it reaches the DB. Revoking a `pg_catalog` function needs a superuser; on a managed Postgres (stage 5) this must be re-checked. New tables read by agent views need a policy.

## 017 — Kaggle distributions: stdlib lognormal fits
**Context:** the generator needs realistic CTR, CPC, CPM and CVR; the Kaggle dataset has no dates, so only ratios can be used.
**Decision:** `generator/build_distributions.py` drops unusable rows (zero clicks, zero or negative spend, impressions below clicks), computes per-row ratios and stores moments, percentiles and a lognormal fit (MLE on ln x, stdlib only, no new dependency) in the committed `generator/distributions.json`. Exact zeros (CVR) are recorded as `zero_share` and excluded from the fit. The CSV is never committed and tests read only the JSON.
**Consequences:** CI needs no dataset; lognormal fits CPC loosely (see `ks_distance`), which is acceptable for synthetic data.

## 018 — Local Postgres bound to localhost only
**Context:** Docker Compose published Postgres on all interfaces (`0.0.0.0`), which is unnecessary for local development.
**Decision:** bind the host port to `127.0.0.1` only (`127.0.0.1:${POSTGRES_PORT}:5432` in `docker-compose.yml`).
**Consequences:** the database is reachable from the host machine but not from other devices on the network.

## 019 — Ruff + pre-commit as the lint gate
**Context:** stage 0 needs a single, reproducible style/lint check for agents and humans.
**Decision:** configure ruff in `pyproject.toml` (line-length 100, target `py312`, select `E,F,I,UP,B`, ignore `E501`); `make lint` / `make format` wrap ruff; `.pre-commit-config.yaml` runs ruff `--fix` and ruff format.
**Consequences:** one tool for lint and format; CI and local hooks share the same rules.

## 020 — CI on GitHub Actions with a throwaway Postgres
**Context:** PRs need `migrate` + `lint` + `test` without local Docker or repository secrets.
**Decision:** `.github/workflows/ci.yml` runs on push to `main` and on pull requests; one `test` job on `ubuntu-latest` with a Postgres 16 service container and throwaway credentials/passwords in the workflow env.
**Consequences:** every PR gets a green/red check; no secrets to rotate for the basic pipeline.

## 021 — Config default tests ignore the outer environment
**Context:** CI sets `APP_ENV=test`; a settings-default test failed because it inherited that value.
**Decision:** tests that assert Settings defaults clear those env vars with `monkeypatch.delenv(..., raising=False)` before constructing `Settings(_env_file=None)`.
**Consequences:** default-value tests pass locally and in CI regardless of workflow or shell env.

## 022 — Kaggle gives the shape, config.yaml gives the level
**Context:** the Kaggle dataset's absolute levels are unrealistic for EUR ad buying (CTR ≈ 0.02%, CPM ≈ 0.3), but its spread is still a useful hint of how much campaigns differ.
**Decision:** `generator/world.py` keeps the lognormal `sigma` from `distributions.json` and sets the mean per platform from `ratios` in `generator/config.yaml` (e.g. Meta CPM ≈ 6 EUR, CTR ≈ 1%) using `mu = ln(mean) − sigma²/2`. Base CPM/CTR/CVR are sampled once per campaign; days wobble around the base with `sigma × daily_ratio_sigma_factor`. CPC is derived (spend / clicks), never sampled, so ratios stay consistent. CVR is capped so conversions ≤ clicks; Kaggle `zero_share` sets the chance of a zero-conversion day.
**Consequences:** realistic magnitudes with data-driven variation; levels are tuned in one YAML file without rebuilding `distributions.json`.

## 023 — Deterministic generator: per-entity RNG streams, Decimal at generation
**Context:** the same seed must always produce the same world (plan §5.1), and later steps (documents, errors) must not shift when the client list changes.
**Decision:** every entity draws from its own `random.Random("<seed>:<kind>:<key>")` (string seeds are SHA-512-hashed, independent of `PYTHONHASHSEED`). Clients are listed explicitly in `config.yaml`. Money is quoted in YAML, parsed to `Decimal` and quantized to cents (`ROUND_HALF_UP`) when generated; the daily plan's rounding remainder goes to the last day so Σplan equals the IO budget exactly. One campaign per IO, `campaign_ref` = `{CLIENT}-{PLATFORM}-{YYMM}`. Delivery dates are the ad account's local dates. `world_digest()` (SHA-256 of canonical JSON) fingerprints a world. PyYAML becomes a runtime dependency to read `config.yaml`.
**Consequences:** reproducible worlds testable by digest; adding a client does not change other clients' data; pipeline and reconciliation can compare money exactly.

## 024 — Generated documents: deterministic PDFs/xlsx, ground truth as exact strings
**Context:** task 1.2 renders the true world into what an agency sees (Excel plans, platform and agency invoices, credit notes). Later steps load the ground truth (stage 1), score LLM extraction against it (stage 2) and plant errors into the documents (task 1.3), so documents must be reproducible and exactly consistent with the world.
**Decision:**
- Libraries: `reportlab` (PDF; `invariant=1` drops timestamps and random IDs), `openpyxl` (xlsx; also needed to read plans in task 1.7), `pypdf` (dev only, tests read PDF text). DejaVu Sans is committed under `generator/fonts/` because the built-in PDF fonts cannot show Lithuanian letters.
- xlsx determinism: write via `ExcelWriter` with fixed core properties (`Workbook.save` stamps "now") and re-zip with fixed entry timestamps. `manifest.json` lists the sha256 of every file.
- Ground-truth JSON stores money as strings (`"1234.56"`) so it parses back to the exact `Decimal`. VAT = `subtotal × 21%`, `ROUND_HALF_UP` to cents.
- Platform invoices: one per ad account × month, lines = delivered spend per `campaign_ref` in the account (= platform) timezone. Three layouts (Meta-, Google-, TikTok-like) differ in headers, column order, number format and wording. Vendors are the configured platform names only (no real legal entities, addresses or logos), and every PDF has a "synthetic test document" footer.
- Client-owned clients get only a media plan: the platform bills them directly, so there is no platform invoice to the agency and no agency invoice.
- Agency invoices: media lines at platform cost per `campaign_ref`, then a negative line per credit note of that period, then one fee line: "Agency commission X% on media" (markup on media net of credits) or "Management fee". Credit notes (count in config) are issued after the platform invoice and before the client invoice of the same period.
- Numbers come from per-entity RNG streams (decision 023) in platform-specific formats; agency numbers are `{prefix}-{CLIENT}-{YYMM}`. Which invoices get a credit note is drawn from one stream over all platform invoices, so changing the client list can change that choice.
**Consequences:** same seed → byte-identical `data/generated/`; reconciliation can compare JSON amounts exactly; error #5 (wrong markup) and #6 (credit not applied) have a dedicated line to corrupt.

## 025 — Planted errors: separate pass, one error per slot, answer key as a file
**Context:** task 1.3 plants errors #1–#9 (plan §5.2) and records each in an answer key. Some errors need a daily-granularity representation; the answer key must stay out of reach of application code (rule 8), and no DB role may write `eval` (decision 004: `eval_runner` is read-only).
**Decision:**
- `generator/errors.py` is a pure pass over the clean world and documents; it returns planted copies and never mutates its inputs. `make generate` (`python -m generator`) runs world → documents → errors → files. The platform API data is written as reported delivery per ad account (`data/generated/delivery/<platform>/<account_id>.json`, no `campaign_ref`); mock APIs (task 1.4) serve it.
- Representation: **#4** the campaign's last-day row is re-dated to the 1st of the next month (whole day; the invoice still bills it; final month excluded). **#9** 1–3 consecutive mid-month rows are absent from the API; the invoice still bills them, so the answer key notes the invoice-vs-delivery gap as a side effect. **#8** clicks ÷ 1.8 at unchanged spend for 3 days (CPC ×1.8, invoices unaffected); magnitude = spend × (1 − 1/1.8). **#7** the same monthly total is re-split over the first 60% of days (zero-spend rows after), so invoices are unaffected; magnitude = peak cumulative overpacing. **#3** from a mid-month day the API reports a new name without the `[campaign_ref]` tag, same campaign id. **#5** the fee line uses contract % ± 2–5 pp and shows that %; magnitude is signed. **#6** the credit line is removed and the markup recomputed.
- Cascade rule: client invoices come from true delivery, so platform-side errors (#1, #2) do not spill into them. Magnitudes are EUR net of VAT.
- Counts: per type `max(errors.min_per_type, round(error_rate × candidates))` (half up; `min_per_type` default 3), capped at the candidates still available; all of them are used if fewer than `min_per_type`; `ConfigError` only when a type has zero candidates. Each error claims `(client, platform, month)` slots (#5/#6 the whole client-month, #4 also the next month); platform invoices with a credit note are excluded from #1, #2, #4. One RNG stream per type and per entity (decision 023); allocation order is fixed, most constrained first.
- The answer key is written only to `data/generated/answer_key.json`. In task 1.11 `evals/load_answer_key.py` loads it into `eval.answer_key` as the DB owner (`DATABASE_URL`), delete + insert in one transaction, run by `make eval-stage1`. Roles and grants are unchanged.
**Consequences:** each planted entity has exactly one answer-key row and the changed PDF/JSON stay consistent; the owner-run loader is the only writer of `eval`. Pipeline loaders must read only `invoices/`, `credit_notes/`, `plans/` and `delivery/`, never `answer_key.json`. `round(0.05 × candidates)` means small pools get exactly `min_per_type`.

## 026 — Mock platform APIs: file-backed, deterministic faults per platform
**Context:** task 1.4 needs Meta-, Google- and TikTok-style APIs (plan §5.3) so the pipeline practises real ingestion. The app must serve the reported delivery files and stay away from the database and the answer key.
**Decision:**
- `mock_platforms/` is a separate FastAPI app with its own `MOCK_PLATFORMS_*` settings (`app.config` requires `DATABASE_URL`). It is configured with the `delivery/` directory itself and only reads `<platform>/*.json` below it, once at startup.
- Dates in the files are already account-local (decision 023) and TikTok accounts are UTC, so the app reformats dates and never converts timezones. Request date params use the same format as the platform's rows. Ranges are inclusive at both ends.
- Rows share field names across platforms; only spend and the date format differ. `spend` and `cost` are decimal strings, `cost_micros` a JSON integer, so money never passes through a float.
- Faults: the nth authorised request on a platform draws from `random.Random("<seed>:<platform>:<n>")`. Auth runs first, so rejected calls do not advance the sequence, and counters are per platform, so one platform's traffic cannot shift another's faults. `MOCK_PLATFORMS_FAULTS_ENABLED=false` turns them off.
- `httpx` is added to the dev group because FastAPI's `TestClient` requires it.
**Consequences:** fault sequences repeat only for the same request order since startup, and a restart resets them. Regenerating data requires restarting the app. Tests build their own files because `data/` is gitignored and absent in CI.

## 027 — Raw responses: one replaceable snapshot per account and period, exact bytes kept
**Context:** task 1.5 stores every API response page. Accounts each restart at page 1, so `UNIQUE (run_id, page)` could hold only one account per run, and the payload does not say which account it came from. JSONB reorders keys and drops whitespace, so it cannot keep a response as received. Rule 10 and plan §7 require that running twice gives identical row counts.
**Decision:**
- Migration `0003` adds `account_id`, `period_start`, `period_end` and `body` (BYTEA, the exact response bytes) to the three raw tables. `payload` stays for querying and is cast from the response text in SQL, so numbers never pass through a Python float. The unique key becomes `(account_id, period_start, period_end, page)`.
- A run replaces the snapshot: all pages of an account are fetched first, then one transaction deletes that account + exact period and inserts them. A failed account stores nothing and keeps its previous snapshot, because a partial account would look like missing delivery days downstream.
- Retries: `backoff = min(cap, base × 2^(n-1))` per error kind and request, no jitter. 429 waits `max(Retry-After, backoff)`, so the cap never shortens the server's wait; 5xx and network errors wait for the backoff. Other statuses and malformed bodies fail at once. Defaults: base 1 s, cap 30 s, 6 attempts for 429, 4 for 5xx.
- Platform and account problems become entries in `IngestResult.failures`; only infrastructure errors (database down) abort the run. A body Postgres refuses (`DataError`, e.g. `\u0000` in JSONB) is an account failure.
- `httpx` moves to the runtime dependencies because `pipelines/ingest.py` imports it in production. The client is synchronous to match plain-function steps (decision 008); `httpx.ASGITransport` is async-only, so tests call the app in-process through FastAPI's `TestClient`, which is an `httpx.Client`.
- `create_etl_engine()` derives the `etl` login from `DATABASE_URL` and `ETL_DB_PASSWORD`.
**Consequences:** raw row counts are stable across runs but only the latest fetch is kept, so earlier responses cannot be replayed. Replacement matches the exact period: a run over a different period is a separate snapshot, and normalization must not sum overlapping ones. `pages_fetched` and `rows_seen` include pages of an account that later failed, so they can exceed what is stored. `etl` cannot write `app.*`, so the runner (task 1.10) needs another role for `app.pipeline_runs`.

## 028 — Normalization: reference file, newest snapshot owns its period, findings written by `app`
**Context:** task 1.6 fills `core.campaigns` and `core.daily_delivery`, but platform data does not say which client owns an account, and no document covers every client: Excel plans have no account ids, industry or fees, and client-owned accounts have no platform invoices. `etl` cannot write `app.*`. Metric columns are `NOT NULL`, so a null metric cannot reach `core`. Snapshots of different periods can overlap (decision 027).
**Decision:**
- The generator writes `data/generated/reference.json` (clients, platforms, ad accounts), standing in for the agency's registry. It is built from the world and carries no error information. This adds one file to the list in decision 025 that pipeline loaders may read. `pipelines/reference.py` upserts it as `etl` before normalizing.
- `METRIC_MAPS` in `pipelines/normalize.py` is the source of truth for field mapping; `core.platforms.metric_map` stores a copy. Spend is strict: decimal strings or integer micros, never a float, quantized to cents with `ROUND_HALF_UP`.
- Dates stay account-local as reported, with no conversion (decision 023). This replaces the "timezones -> UTC and agency date" wording in task 1.6; reconciliation joins `core.ad_accounts.timezone` when it needs it.
- Snapshots of an account are read newest first, and a newer snapshot owns every date in its period, so a day it omits stays missing rather than being filled from an older one.
- A campaign is keyed by `platform_campaign_id`. `name` is the earliest reported name, which carries `[campaign_ref]` for task 1.7; other names become aliases (`source='rule'`, confidence 1). `io_id` stays NULL and is outside the upsert's `SET`.
- Null metrics stay on the in-memory record, are not upserted and still reach quality. Unreadable rows and accounts missing from the reference data are reported, never guessed.
- Quality checks are pure. `quality.write_findings` logs in as `app` and upserts on `dedup_key` (with the reason appended for rejected rows); status and decision columns are never updated. Grants are unchanged. A one-day gap at month end whose only later row is the 1st of the next month is `month_boundary_shift` rather than `missing_days`.
**Consequences:** the active span is first to last reported day, so a gap at the very start or end of a flight is invisible until IO dates exist. Upsert-only means a day that disappears from a later snapshot stays in `core`, though quality still reports it. An issue whose problem goes away stays open. Trailing zero-spend runs also fit pacing drift, so task 1.11 must decide how `quality_zero_spend` counts. `core.clients` has no `code` column while plans and invoices use `client_code`; `reference.json` keeps the code and task 1.7 must resolve it.

## 029 — Plan and invoice loading: client codes, documents as written, ownership of columns
**Context:** task 1.7 loads Excel plans and invoice documents into `core`. Both identify clients by `client_code`, which `core.clients` did not have, and the local database already held clients. A real agency has only PDFs, but extraction arrives in stage 2. Planted errors must reach `core` untouched for task 1.8 to find them.
**Decision:**
- Migration `0004` adds `core.clients.code` (unique, NOT NULL). Existing rows are matched by name to `reference.json` and the migration aborts if one cannot be matched; an empty table never reads the file. `upsert_clients` now conflicts on `code`, so a renamed client stays the same row. Roles, grants and RLS are unchanged.
- Stage 1 reads the `.json` next to each PDF, under `invoices/` and `credit_notes/` only. It is a stand-in for extraction and holds what the document says, planted errors included. `file_path` stores the PDF path relative to the data directory.
- Nothing is validated against anything else: duplicates, wrong markup and unapplied credits load as written. `credit_notes.amount` is the note's net `subtotal`, positive as printed, because the credit line on client invoices is `-subtotal` and reconciliation is net of VAT.
- openpyxl returns numeric cells as int or float, so `Decimal(str(value))` runs at that boundary and is quantized to cents; no float goes further. JSON money must be a decimal string.
- An unreadable document is rejected whole and reported in the result, and the run continues. Two files with the same vendor and number cannot both be stored: the first in path order is kept and the other is reported.
- Upserts leave `invoices.status`, `invoice_lines.campaign_id`, `invoice_lines.extracted_confidence` and `insertion_orders.rate_type` alone. Lines a re-loaded invoice no longer has are deleted.
- Plan loading sets `campaigns.io_id` from the `[campaign_ref]` tag in `campaigns.name`, matched on client, platform and ref. A campaign with no tag, no matching IO, or a ref fitting several IOs is counted as unlinked and not guessed.
**Consequences:** a migration can depend on a gitignored file when the table has rows. An invoice whose file disappears stays in `core`. A credit note's `campaign_ref`, period and VAT are not stored; the original invoice gives the period. Rejections live only in the result objects until the runner (task 1.10) records them. Plans must load after normalization for campaigns to link. `invoice_lines.campaign_id` stays NULL until task 1.8.

## 030 — Reconciliation: account-local delivery, one issue per problem, rules separate from writers
**Context:** task 1.8 compares invoices with delivery per client × platform × month. Plan §8 asked for delivery in both the platform and agency timezone, but rows are per day in the account's local dates and cannot be re-bucketed. One problem can surface in several places: a day dated across a month end moves delivery in two months and already has a quality issue, missing days have a quality issue and also lower delivery, and a duplicate invoice also inflates the invoiced amount. The task is split into 1.8a (linking, duplicates, invoice vs delivered, writers) and 1.8b (budget and client invoice rules), which extends this entry.
**Decision:**
- Rules are pure functions over dataclasses in `backend/app/reconciliation/`, and every threshold is in its `config.py`. `pipelines/reconcile.py` does the reading and writing, because `pipelines` imports `app` and never the reverse.
- `delivered` is account-local only. Invoices use the same timezone, so a real offset creates no invoice-vs-delivery variance; what is visible is a whole day landing across a month end. "Variance ≤ boundary-day spend" was rejected because one day is about 3.3% of a month, the same size as real overcharges.
- The evidence comes from quality's own `check_missing_days` and `dedup_key`, run over `core`, so a problem cannot be defined or keyed two ways.
- Rule 1 removes shifted days first (only if that shrinks the variance), then missing days, and only then reports a variance. Comparisons are strict, on the exact Decimal, against delivered.
- A matching shift upserts onto the quality issue's key and sets `type` to `reconciliation_timezone_shift` (account timezone differs from `agency_timezone`) or `reconciliation_month_boundary_shift` (same timezone, so timezone cannot be the cause). The next month's opposite variance gets no issue. `core.reconciliation_results` keeps the uncorrected variance and `status='issue'` in both months. Variance left after the shift is a separate issue.
- A positive variance of at most missing days × the campaign's highest daily spend (`missing_days_limit`) is added to the earliest `quality_missing_days` issue, which keeps its type. A larger one is an overcharge. A missing-days note only updates an existing issue and never inserts one.
- Duplicates are computed first: same kind, vendor, client, platform, period and net amount, different number. The earliest issued is the original; undated invoices count as copies.
- `invoiced` is the sum of lines, net of VAT and before credit notes.
- Status: `issue` if a rule fires; `incomplete` if delivery is absent or an agency-billed month has no invoice (no issue); client-owned months without an invoice are `ok`.
- Lines link by client, code and (on platform invoices) platform to the order's one campaign. Only found links are written, so a later manual link is not cleared. Issue upserts leave status and decision columns alone and have their own column list, because quality's omits `amount` and `type`. `quality.py` is unchanged and no migration is needed.
- 1.8b, rule 2 (delivered vs IO budget): `planned` is the sum of the slot's one-month orders. An order spanning months leaves `planned` NULL in every month it touches and the rule does not run there; its budget is not prorated or guessed. The rule fires when delivered is strictly below 85% or above 115% of `planned` (`BUDGET_MIN_SHARE`, `BUDGET_MAX_SHARE`), as `reconciliation_budget_overspend` or `_underspend`, keyed `reconciliation:budget:{client}:{platform}:{YYYY-MM}`. It applies to every billing model, and is the only rule client-owned clients get.
- 1.8b, rule 3 (client invoice vs billing model), per agency-billed client × month over the kept client invoices; a second invoice that is not a duplicate is combined with the first. A line without a code is the fee, a negative coded line is a credit, a positive one is media; coded lines get their platform from the client's order with that code. Two checks, each with its own base, so one removed credit is one issue:
  - Fee, client-level (`platform_id` NULL, key `reconciliation:client_fee:{client}:{YYYY-MM}`, type `reconciliation_wrong_markup`, also for a wrong management fee): the fee lines against `markup_pct` × the invoice's non-fee lines as printed (media less the credits it applies), half up to cents, or against `mgmt_fee`.
  - Credits, per platform (key `reconciliation:credit:{client}:{platform}:{YYYY-MM}`): the stored credit notes of the slot's kept platform invoices against the credit lines for that platform. More missing is `reconciliation_credit_not_applied`, more applied is `reconciliation_credit_over_applied`; the amount is the credit difference only, and the text names the commission charged on it. A note on a duplicate copy is not expected on the client invoice.
  - Both fire only when the difference is strictly above EUR 1.00 (`CLIENT_INVOICE_MIN_EUR`), with no percentage test.
- 1.8b, client columns: `client_invoiced` per platform is that platform's net lines plus a share of the invoiced fee; `expected_client_amount` is its media less its stored credit notes plus a share of the fee due on the sum of those. The fee is shared in proportion to net media by largest remainder in cents (ties by platform name; equal shares when a weight is negative or the weights sum to zero or less), so the rows of a client-month add up exactly. **This share is a convention**: the fee belongs to the client-month, not to a platform, which is why fee issues are client-level. If a non-fee line has no platform, both columns stay NULL for that client-month and the credit check is skipped; the line has a `needs_matching` issue and the fee check still runs.
- 1.8b, status: a client-level issue marks every row of its client-month as `issue`. After the issue checks, an agency-billed month with no client invoice is `incomplete` with no issue; a variance above the rule 1 thresholds still makes it `issue`. Client-owned months get no client columns.
**Consequences:** task 1.10 must run quality before reconcile; quality rewrites the shared issue's text and severity each night and reconcile restores them, so only the end of a run is stable. A variance with missing days but no quality issue, such as a null-metric day that quality reports as `null_values`, creates no second issue; its amount is recorded on no issue and is only counted in `ReconcileResult.gap_notes_unattached`, so task 1.10 must record and report that count. Task 1.11 must count both `reconciliation_timezone_shift` and `reconciliation_month_boundary_shift` as error #4. Rule 2 does not run for orders spanning months until a proration rule is chosen. Task 1.11 must count `reconciliation_credit_not_applied` as error #6 and `reconciliation_wrong_markup` as error #5. An invoice spanning months counts in the month it starts. Results and issues are two transactions, repaired by re-running. As in decision 028, an issue whose problem goes away stays open.

## 031 — Pacing: per insertion order, explicit as-of date, closed flights report red trajectories only
**Context:** task 1.9 adds pacing (plan §9). The generated delivery covers 2026-05-01 to 2026-10-31 for every account, with no November rows. All 114 orders are whole calendar months, none spans months, and all are linked to a campaign. So with the last delivered date as the default, every flight is closed. Planted error #7 keeps the month total and only moves the timing, so it never shows in a month total. Rule 2 (delivered vs IO budget) and `quality_zero_spend` already cover parts of the same campaign-months.
**Decision:**
- Rules are pure functions over dataclasses in `backend/app/reconciliation/pacing.py`. Weekday weights, the 7-day window, the minimum day and the status bounds are in its `config.py`. `pipelines/pacing.py` logs in as `app` only, which can read `core` (decision 004 grants), and reuses reconcile's `issue_row` and column list.
- The unit is one insertion order: its linked campaigns' rows inside its own dates. The daily plan is budget × weekday weight over the flight days. An order spanning months is paced over its whole flight; this needs no monthly budget, so `planned` stays NULL as decision 030 says. Its key month is its start month.
- `as_of` is a required argument of the rules. The step defaults it to `MAX(core.daily_delivery.date)` and returns the date it used. It never reads the clock.
- Forecast = actual + average × remaining days. The average divides by the reported days among the last `min(7, elapsed)` days: a reported zero counts, a missing row is unknown and is skipped, and no reported row gives 0. Each bound belongs to the milder status.
- Issues start only from day 7 of the flight. Running the rules on today's data showed that days 1–6 gave 4 false reds and about 15 false yellows a month. Running flight: a red or yellow status now, or a red on any earlier day, raises an issue. Closed flight (`as_of ≥ end_date`): only a red day raises one, and only when the final total is inside rule 2's band (`BUDGET_MIN_SHARE`..`BUDGET_MAX_SHARE`) or the order spans months. A total outside the band is rule 2's issue. Closed yellows are not reported: in today's data they are noise at 96–98% (34 orders), plus 10 final totals at 90–97% that come from month-boundary shifts and missing days.
- Key: `pacing:{client}:{platform}:{campaign_ref}:{YYYY-MM}`, with no status, type or amount in it. Types are `pacing_overpacing` / `pacing_underpacing`, from the flagged day's forecast vs budget. Severity: red high, yellow medium. Amount: the gap between cumulative actual and plan on the as-of date for a running flight, and the signed peak gap for a closed one. The peak gap is the same measure as the generator's #7 magnitude.
- One problem, one issue (the decision 030 shift pattern): the step runs quality's own `check_zero_spend` and `dedup_key`. When an order has a zero-spend run that starts inside its flight and on or before the as-of date, the draft is written onto the earliest run's quality key, so type, severity, amount and text become pacing's. An exception keeps one problem from becoming two: if a pacing-key issue already exists, it stays in use and the quality issue is left alone. Status and decision columns are never updated.
- An order with no linked campaign or no positive budget is skipped and counted, never read as zero spend. No results table and no migration: `app.issues` has every column needed, and other statuses are only in the step's result.
**Consequences:** on today's data pacing turns the 6 `quality_zero_spend` issues into `pacing_overpacing`, one per month, and adds no other issue, so task 1.11 counts `pacing_*` as #7. Run order is quality → reconcile → pacing. Quality rewrites the shared issue's text and severity each night and pacing restores them. While a flight is running, quality's zero-spend key contains `date_to`, so a growing run gets a new key each night. That is existing quality behaviour and is left as it is. An issue whose status goes back to green stays open, as in 028/030. Nothing exercises an in-flight month end to end. That would need a generator change, with a current month of whole-month orders, delivery only up to a cutoff, no invoices and no planted errors. It would also need a closed-month guard on rule 2, which would otherwise flag every running slot as underspend. Both are left for a follow-up. A slot with several one-month orders is compared with rule 2's band order by order, not on the slot sum.

## 032 — Pipeline runner: one run_id, fixed order, record written by `app`, partial runs
**Context:** task 1.10 wires plan §7 into one run. Until now each step was called by hand with its own `uuid4()`, and `make pipeline` was a stub. Decisions 027–031 left this task several duties: `etl` cannot write `app.*`, rejected documents exist only in result objects, quality must run before reconcile and pacing, and `gap_notes_unattached` and pacing's `as_of` must be reported. Task 1.12 will wrap each step as an Airflow task.
**Decision:**
- `pipelines/run.py` has one `step_*` adapter per step. Each takes a `RunContext` (run_id, data dir, `etl` and `app` engines, ingest HTTP client and settings, agency timezone, optional `as_of`), calls the existing engine-taking function and returns its counts. `STEPS` fixes the order once: reference → ingest → normalize → quality → load_plans → load_invoices → reconcile → pacing. The reasons are in the code: normalize needs the accounts, plans link the campaigns that normalize creates, and reconcile and pacing update the issues quality wrote. The `*_from_env` functions are unchanged.
- One `run_id` per run, used both as `app.pipeline_runs.id` and as the `run_id` of every row the steps write. The record is inserted as `running` before the first step and updated when the run ends, both through the `app` engine. The existing `details` JSONB holds `data_dir`, each step's name, status, duration and counts, and the error. Duration is `finished_at − started_at`. No migration is needed.
- Failures: the first step that raises stops the run. It is recorded as `failed` with `"{Type}: {message}"` (at most 2000 chars), and the record is written in a `finally`. Ingest raises `IngestUnavailable` when no platform could list its accounts, because otherwise a run against a stopped API would quietly reuse old snapshots. Account or platform failures and rejected plan or invoice documents let every step run: failed accounts keep their previous snapshot (decision 027), and the run is `partial`. Rejected rows and unknown accounts do not make a run partial, because they already become quality issues. Exit codes of `python -m pipelines.run`: 0 succeeded, 1 failed, 2 partial. `make` turns any non-zero recipe status into its own 2 (it prints the real code as `Error 1` / `Error 2`), so `make pipeline` only tells success from non-success; a scheduler that must tell failed from partial calls the module or reads `app.pipeline_runs.status`.
- The mock platform API is an external service. `make pipeline` expects `make mock-apis` to be running and does not import `mock_platforms`. Tests inject a `TestClient` as the ingest client.
- `make pipeline` is `PYTHONPATH=backend uv run python -m pipelines.run`. Every settings class already reads `.env` from the working directory. `--data-dir` and `--as-of` are optional arguments.
**Consequences:** a process that is killed leaves a `running` row with no steps. Quality is the one step that needs another step's in-memory result (normalize's rejected rows and unknown accounts are not stored), so task 1.12 must run normalize and quality in one Airflow task or store those first. With faults on, a long backoff sequence can make a nightly run partial without anything being wrong with the data, and the record shows which accounts were affected.

## 033 — Stage 1 eval: issue types per planted error, latest run only, counts-only results
**Context:** task 1.11 measures stage 1 (plan §11): every rule-detectable planted error found, ~no false alarms. Decision 025 left the loader to this task; decisions 030 and 031 named which issue types count for #4, #5, #6 and #7. `eval.answer_key` has no columns for the client, platform, error number or stage. Issues are upsert-only and stay open after their problem goes away, so the database can hold issues from earlier runs or seeds. If an agent could see which planted errors the rules miss, it could tune the rules to the answer key.
**Decision:**
- `evals/load_answer_key.py` (`make eval-load-key`, owner only) replaces `eval.answer_key` in one transaction. `client_code`, `platform`, `error_no`, `entity_type`, `detectable_in_stage` and the seed go into `details`, with the generator's own details under `planted`. No migration; roles and grants unchanged. The loader is its own target, not part of `make eval-stage1` as 025 said, so the eval process never holds owner credentials. Money must be a decimal string; any JSON float is rejected.
- `evals/stage1.py` (`make eval-stage1`) logs in as `eval_runner` and reads only open issues of the latest `succeeded`/`partial` run in `app.pipeline_runs`; issues of other runs are counted in a note only.
- An issue matches a planted error when its type is accepted for that error and client code, platform and month are equal, plus an entity check: #1 `reconciliation_overcharge`; #2 `reconciliation_duplicate_invoice` with `entity_id` = the copy's number; #4 `reconciliation_timezone_shift` or `_month_boundary_shift` with `entity_id` = platform campaign id; #5 `reconciliation_wrong_markup` with no platform (client-level); #6 `reconciliation_credit_not_applied` on the credit note's platform; #7 `pacing_overpacing` on the issue's order code = campaign_ref (see the fix below; narrows 031's "pacing_*": underpacing is the wrong direction for drift); #9 `quality_missing_days` with `entity_id` = platform campaign id.
- Errors with `detectable_in_stage` above 1 (#3, #8; #10 when planted) are "expected missed" and never fail the run.
- Matching is one-to-one and greedy: errors in (error_no, entity_ref) order, issues in id order. One issue never counts for two errors; a second issue for a found error is a false alarm ("duplicate detection"). Every other unmatched issue is a false alarm, shown under the error type its issue type stands for, or under "other issue types".
- A `quality_month_boundary_shift` left on a planted #4 or a `quality_zero_spend` left on a planted #7 means the error is missed, but that issue is reported as misclassified and is not counted again as a false alarm.
- Exit 0 when nothing must-find is missed and false alarms ≤ `--max-false-alarms` (default 0); exit 1 otherwise; exit 2 when there is no answer key or no finished run.
- The run writes `docs/eval-results.md` itself: run id, seed, per-type counts, € sums (`Decimal`) and the verdict, with no entity refs. Which entities were missed or falsely flagged is printed to the terminal only. `backend/tests/test_eval_isolation.py` fails if `pipelines/`, `backend/app/` or `mock_platforms/` mention the answer key, the `eval` schema or `evals`; only the ORM table definition is allow-listed.
**Consequences:** stage-1 acceptance is `make eval-stage1` exiting 0, run by the owner after `make generate`, `make eval-load-key` and `make pipeline`. Agents develop the eval against hand-built keys only and never see the real results per entity. The greedy matching is not optimal in general, but slots never carry two errors (025), so it cannot matter on generated data. Re-loading a key from another seed without re-running the pipeline is not detected; the results file shows both the seed and the run.
**Fix (#7 matching):** a drifted campaign always has a zero-spend tail, so pacing takes over the `quality_zero_spend` issue, and the takeover updates neither `entity_type` nor `entity_id`. The row stays `campaign` / platform campaign id and never equalled the answer key's order code, so every #7 was reported missed and every pacing issue as a false alarm. The eval now resolves each issue's order code (`order_ref`): its own `entity_id` for an `insertion_order` issue, otherwise `core.campaigns.io_id` → `core.insertion_orders.campaign_ref` for a `campaign` issue. eval_runner can already read both tables. #7 and its zero-spend precursor match on `order_ref`; the other types still use `entity_id`. Pipelines, rules, roles and grants are unchanged.
**Follow-up:** the pacing takeover keeps the quality row's `entity_type`/`entity_id` (campaign), so pacing issues point at a platform campaign instead of the insertion order. This is to be fixed in a separate pipeline task, not in 1.11.

## 034 — Airflow wrapper: own image with an isolated project venv, normalize+quality as one task, record always runs
**Context:** task 1.12 wraps the nightly pipeline (decision 032) in an Airflow DAG, in a compose profile outside `make up`, without changing `pipelines/`, `backend/app/`, roles, grants or migrations. Airflow pins its own libraries, so it must not enter the project's uv environment or CI. `RunContext` lives in memory for one process, but Airflow runs every task in its own process. Quality needs normalize's in-memory result (032).
**Decision:**
- Image `orchestration/Dockerfile`: `apache/airflow:3.3.2-python3.12` plus a separate venv `/opt/matchbook-venv` built with `uv sync --frozen --no-dev` from `uv.lock`. A `.pth` file puts `backend/` and the repo root on that venv's path only. Project tasks use `@task.external_python` with that interpreter, so step code runs with the project's dependencies and Airflow's pins never meet them. Code is mounted read-only; the image holds dependencies only, and a root `.dockerignore` (allowlist) keeps `.env` and `data/` out of the build context. Airflow is not in `pyproject.toml`; CI is unchanged. Pinned 3.3.2 (latest patch of the mature minor, Python 3.12 supported) rather than 3.4.0, released four days before this task.
- Compose profile `airflow`: one `airflow standalone` container (LocalExecutor, parallelism 4, no examples), its own `airflow-postgres` for metadata (separate from matchbook), and `airflow-mock-apis`, which serves the mock APIs on the compose network through `orchestration/mock_apis_server.py` (`make mock-apis` binds 127.0.0.1). The UI is bound to 127.0.0.1; its `admin` password is generated by Airflow (`make airflow-password`). Secrets come from `.env` via `${VAR:-}`, so `make up` with an older `.env` gives no warnings; `make airflow-up` checks the new variables first.
- No owner credentials in Airflow: tasks get `DATABASE_URL` without user or password and only `ETL_DB_PASSWORD`/`APP_DB_PASSWORD`, which is all `create_etl_engine`/`create_app_engine` need. Only `reference.json`, `plans/`, `invoices/` and `credit_notes/` are mounted (`delivery/` into the mock APIs), never `answer_key.json`.
- DAG `orchestration/dags/matchbook_nightly.py`: `start` → `reference` → `ingest` → `normalize_quality` → `load_plans` → `load_invoices` → `reconcile` → `pacing` → `record` → `outcome`. Each project task body is one call into `orchestration/tasks.py`, which reuses `pipelines.run` (`STEPS`, `RunContext`, `start_run`, `finish_run`, `run_status`, `error_text`). normalize and quality run in one task on one context: the one deviation from one task per step. A test fails if the DAG's steps drift from `STEPS`.
- `start` creates the `run_id` (uuid4) and the `running` row; the id reaches every task through XCom as the task parameter `pipeline_run_id`, and the Airflow run id is kept in `details.airflow_run_id` with `orchestrator: "airflow"`. Each step writes its record (name, status, duration, counts, and on failure the error) as JSON to a run-state volume, then re-raises on failure. XCom alone cannot carry the error of a task that raised. `record` (`trigger_rule="all_done"`) reads the records in `STEPS` order and writes the row with 032's status rules. The first step with no record (killed, timed out, never ran) counts as failed with "step did not report". Task parameters must not use Airflow context-key names (`run_id`, `ti`, `params`, …): the first real run failed in every task because a parameter was named `run_id`, so it is `pipeline_run_id` and a test guards the names.
- Airflow states: succeeded → all green; partial → `outcome` skipped, DAG run success; failed → the failing step failed, later steps `upstream_failed`, the row written, then `outcome` fails (no retry) and so does the DAG run. `outcome` exists because an all_done `record` as the only leaf would mark failed runs green.
- Schedule `CronTriggerTimetable("0 3 * * *")` in `AGENCY_TIMEZONE` (the env variable `Settings` reads; the DAG cannot import `app.config`), `catchup=False`, `max_active_runs=1`, `dagrun_timeout` 3 h. Steps are idempotent, so `retries=2`, `retry_delay` 5 min, `execution_timeout` 1 h; ingest keeps its own HTTP backoff.
- Tests run without Airflow: `test_airflow_dag.py` reads the DAG with `ast` (task layout, trigger rule, schedule, retries, no task parameter named like an Airflow context key, and a thinness guard: no SQL, no project or DB imports, one glue call per task); `test_orchestration_tasks.py` covers the glue. `make airflow-check` lists import errors in the real image and is not part of CI. `test_eval_isolation.py` now guards `orchestration/` too.
**Consequences:** two Python environments in one image; the venv must be rebuilt (`make airflow-up` builds) when `uv.lock` changes. A crash right after `start` inserts its row leaves a `running` row, as with a killed process in 032. Clearing one failed task with its downstream reuses the run id and updates the same row; clearing the whole DAG run starts a new run. Run-state files (a few KB per run) are kept; pruning is a follow-up. If `data/generated/credit_notes/` does not exist, Docker creates it empty on the host. `make airflow-down` removes only the Airflow containers; `make down` does not touch profiled services, so run `airflow-down` first.

## 037 — Malicious invoices in `inbox/` with new numbers, planted last; synthetic PII outside the ground truth
**Context:** task 2.2 adds documents that exercise PII masking (2.3) and prompt-injection defences (2.5, threat model T1), and error #10 to the answer key (T7). Stage 1 loads the ground-truth `.json` next to every PDF under `invoices/` and `credit_notes/` (decision 029). A malicious copy of a real invoice placed there would load as a second invoice, raise `reconciliation_duplicate_invoice` false alarms and fail `make eval-stage1`. The demo seeding (`deploy/demo/init.sh`) runs the same generator and pipeline.
**Decision:**
- #10 is `prompt_injection`, entity `platform_invoice`, detector `extraction_security`, detectable in stage 2. There is one copy per variant listed in `errors.prompt_injection.variants` (config): `white_text`, `tiny_font` (1 pt), `outside_page` (beyond the media box), `metadata` (Subject and Keywords), `visible_note`, `fake_json`, `change_total`. The count is the number of variants, not the rate formula of 025.
- A copy is the original with a **new number** in the vendor's own format (drawn like #2's, collision-checked). The copy keeps every visible value, so its ground truth is the visible values. Payloads are inert constants in `generator/documents/injection.py`, drawn by a `decorate` callback the PDF renderers call before finishing the page. The only URL host is `example.invalid`.
- Copies are written to a **separate top-level folder, `inbox/<platform>/<yyyy-mm>/`**, PDF plus ground-truth JSON, and listed in `manifest.json`. They are not part of `PlantedOutput.documents`. The stage-1 loader, the Airflow mounts and the demo never read `inbox/`, so no pipeline, eval or deploy code changes.
- `plant_prompt_injection` runs **last** and claims its `(client, platform, month)` slot like any error (025). Each type has its own RNG stream, so #1–#9, the stage-1 documents and the delivery stay identical to a run without #10. One answer-key row per copy: `entity_ref` = copy number, magnitude = subtotal (what would be booked twice if the copy got through), details `variant`, `original_number`, `vendor`, `total`.
- Invoices print synthetic contact details: email and phone under the header, IBAN in a "Pay to" footer line. The IBAN is Lithuanian with the bank code `99999`, which no Lithuanian bank uses, and valid mod-97 check digits (ISO 13616). The email is `billing@<vendor-slug>.example` (RFC 2606). The phone is in `+44 20 7946 0000–0999`, a range Ofcom reserves for drama, so it reaches no real person. Values come from a per-vendor RNG stream (023), stored on `Invoice.contact` and **never written to the ground truth** (data minimization: extraction does not need them). The world is unchanged, so `world_digest` is too. PDF bytes change.
- Rejected alternatives: (a) a manifest of files for stage 1 to skip. It needs a pipeline change, and the manifest is a label list app code could read (T7). (b) Unique numbers alone, inside `invoices/`. Stage 1 would load the copies as duplicates.
**Consequences:** `make eval-stage1` gets a `#10 prompt_injection` row counted as expected missed (033), and the demo parser accepts the label. Every file in `inbox/` is malicious for now, so a stage-2 component could "pass" by rejecting on path. To prevent that, the 2.5 scanner and guards take only bytes and text, never a path, and 2.6/2.7 read `inbox/` together with `invoices/`. Clean decoys in `inbox/` are a possible later addition. If a guard ever misses a copy in 2.7, its new number makes it a visible duplicate-invoice issue. A copy with the original number would instead win 029's "first in path order" rule (`inbox/` sorts before `invoices/`) and silently replace the real invoice. The phone format is UK, so 2.3's LT phone pattern needs hand-written test strings.

## 038 — PII masking: `mask(text) -> str`, stateless, mapping private, network-aware card rule
**Context:** task 2.3, threat model T2. The LLM client (2.4) must mask every request, and the mapping must never leak. Invoices print bare digit runs that look like card numbers: Meta account IDs (15 digits) and TikTok advertiser IDs (19 digits). About 1 in 10 of them pass Luhn, and extraction needs them.
**Decision:**
- `backend/app/llm/masking.py` has one public function, `mask(text) -> str`. Each call builds its own placeholder mapping (`[IBAN_1]`, `[EMAIL_1]`, `[PHONE_1]`, `[CARD_1]`, `[PERSONAL_CODE_1]`, numbered by first occurrence; the same normalised value gets the same placeholder) and discards it. Nothing is logged. There is **no public unmask**: the extraction schema has no PII fields, so model output never needs the originals. `_mask_with_mapping` is private and exists for the module's tests.
- Detector order: email, IBAN (mod-97, 15–34 chars), card, LT personal code (checksum), phone (international `+`/`00` with 8–15 digits; LT national `8…` with exactly 9 digits). A match that fails validation is retried cut at each separator, so a trailing date or amount never hides the value before it.
- Card = network prefix and length (Visa, Mastercard, Amex, Discover) + Luhn, grouped or contiguous. A run right after an `ID` label (`Account ID`, `Advertiser ID:`, `Customer ID`) is never a card.
- Every pattern is bounded and starts only at a token boundary, so untrusted text cannot cause catastrophic backtracking.
- `backend/app` keeps its own mod-97 code; it never imports `generator`.
- Rejected alternatives: (a) any 13–19 digits + Luhn: it masks account IDs that extraction needs. (b) grouped or labelled cards only: it misses a bare card number in free text.
**Consequences:** a bare card number printed right after an `ID` label is not masked. A real card prefix + Luhn on a non-card ID without that label would be masked (over-masking, the safe side). `test_masking.py` renders every generated invoice, inbox copy and credit note in a tmp dir and proves exactly the contact details are masked and nothing else.

## 039 — LLM access layer: provider interface, Gemini over plain httpx, guards before any network
**Context:** task 2.4 (decision 010, threat model T2–T6). The owner chose Google Gemini (`gemini-2.5-flash-lite`) for development, with caps of €0.20 per run and €1 per month. Later stages need other providers (Azure OpenAI in stage 5), and tests must run without a key or network.
**Decision:**
- `backend/app/llm/provider.py` defines `ModelRequest` (model, system, user text, JSON schema, output limit, temperature 0), `ModelResponse` and a `Provider` protocol. `ModelRequest` has **no tools field**, so no adapter can send tools (T4). Adapters raise `RetryableProviderError` (429, 5xx, timeout, network) or `ProviderError`, and their messages never quote headers or bodies.
- `gemini.py` calls `models/{model}:generateContent` with **plain `httpx`** (already a runtime dependency, decision 027), not the Google SDK. It is one POST; the body is an explicit dict we can assert on; `httpx.MockTransport` tests it offline; and it adds no package (T8). The key goes in the `x-goog-api-key` header, never the URL. `responseMimeType: application/json` + `responseJsonSchema`, `thinkingConfig.thinkingBudget = 0`, thought tokens billed as output. The body is read in chunks and refused above `LLM_MAX_RESPONSE_BYTES`. `default_http_client` is the one place a real client is built; the test conftest replaces it.
- `LLMClient.complete_json(task, prompt_id, text, schema)` runs, in order: schema must be pydantic with `extra="forbid"` → input length ≤ `LLM_MAX_INPUT_CHARS` → `masking.mask` (2.3) → versioned prompt file → price lookup (an unpriced model is refused, never assumed free) → per attempt: cost check, then the provider → pydantic validation. Invalid JSON, extra fields or an unfinished answer get **one** more call, then `LLMOutputInvalid`; there is no repair loop (T3). The tracer gets an event with masked input and masked output only, and a tracer error never fails the call.
- Cost (`cost.py`): `Decimal` EUR price per million tokens per model in `Settings.llm_prices_eur_per_mtok`. Before every attempt `CostLedger.check` refuses the call if `run total + worst case > run cap` or `month before this run + run total + worst case > monthly cap`. Worst case = input estimated as UTF-8 bytes / 2 (above any real tokenizer, no extra API call) plus the full `max_output_tokens`. After the call the real cost from the provider's token counts is recorded. `monthly_spend(engine, now, tz, exclude_run_id)` sums `app.pipeline_runs.cost_eur` from midnight on the 1st in agency time, without the current run so it is never counted twice; the pipeline (2.7) passes it into the ledger.
- Prices are paid list prices (USD used as EUR, rounded up). The free tier really costs nothing, but caps computed at list price keep the guard meaningful when the key moves to a paid tier.
- Retries copy decision 027's policy (base 1 s, cap 30 s, 6 attempts for 429, 4 for 5xx, 429 waits `max(Retry-After, backoff)`). Gemini's `RetryInfo.retryDelay` in the error body counts as Retry-After. A requested wait above `LLM_MAX_RETRY_WAIT_SECONDS` (60) fails the call instead of sleeping. The policy is a small copy, not an import from `pipelines/ingest.py`, because `backend/app` does not depend on `pipelines`.
- Prompts are `backend/app/llm/prompts/<name>_v<N>.md`; the id pattern keeps lookups inside that folder and the SHA-256 goes into every `LLMResult`.
- A missing or blank `GEMINI_API_KEY` raises `MissingApiKeyError` in `create_llm_client`; there is no default. Tests use `FakeProvider` (scripted answers, records every request); an autouse fixture removes the key from the environment and blocks real clients. `test_llm_isolation.py` forbids provider/Langfuse SDK imports and provider URLs outside `backend/app/llm/`.
- gitleaks (v8.30.1) runs in pre-commit on staged changes.
**Consequences:** adding a provider is one adapter plus a `llm_provider` literal and a price entry. `responseJsonSchema` support is provider-side and not proven offline; pydantic validation in code is the control that matters either way. The input estimate overstates cost, so a run can be refused slightly before it would really reach the cap (the safe side).

**Context:** a live call to `models/gemini-2.5-flash-lite` (039's default) returned HTTP 404: Google says the model is "no longer available to new users". The owner's key gets HTTP 200 from `models/gemini-3.1-flash-lite`.

## 042 — Invoice extraction: pypdf at runtime, hidden-text scan and guards before the model, confidence in code
**Context:** task 2.5 (threat model T1–T5, T8). One PDF must become a structured result the pipeline (2.7) can load, without letting document text steer the model or a model answer reach `core` as fact. The generator plants seven injection variants (decision 037). `pypdf` was a dev dependency (decision 024).
**Decision:**
- **Library:** `pypdf` moves from the dev group to runtime at the locked 6.21.4 (`uv add` alone resolved 7.0.1; the lock was pinned back so the reviewed version ships). Pure Python, already locked, and its content-stream visitor reports each operator with the CTM and text matrix, which the hidden-text scan needs. Rejected: pdfplumber (adds pdfminer.six and the pypdfium2 binary), PyMuPDF (AGPL, native code). The demo image (`uv sync --no-dev`) now installs it.
- **Input:** `extract_invoice(pdf: bytes, client, config, known_campaign_refs=None)` and `extract_invoice_text(text, ...)`. No path or file-name parameter: only content counts (037). Size (`EXTRACTION_MAX_PDF_BYTES`, 5 MB) is checked before parsing, then page count (`EXTRACTION_MAX_PAGES`, 5); encrypted or unparseable → `failed`.
- **Hidden text** (`pdf_text.py`): a tracker follows fill/stroke colour, render mode, font size and fill alpha through `q`/`Q` and form XObjects, and flags any text-showing operator with a non-empty string drawn in render mode 3/7, white (stroke colour for outline modes), with an effective size below 2 pt, with fill alpha below 0.1, or with its origin outside the media box. Text is never decoded for this; undecoded bytes count as text. Metadata values go through the content guards.
- **Content guards** (`guards.py`): bounded regexes on NFKC-normalised, casefolded, whitespace-collapsed text with format characters (zero-width, bidi) removed: instruction phrases (ignore instructions, system prompt, addressing an AI, role play, skip checks, approval wording, change a value), a quoted JSON key, URLs, and a spoofed `<document>` tag. Findings hold rule codes only, never the matched text.
- **Any finding → `rejected`**, and the model is never called. This is stricter than "flag and lower confidence": the threat model and task require rejection before any LLM call.
- **Model call:** the text is wrapped in `<document>…</document>`; the prompt (`invoice_extraction_v1`) says everything inside is data. `LLMClient` masks it, sends no tools and validates `InvoiceExtraction` (strict, `extra="forbid"`, money and dates as pattern-checked strings, length limits, at most 50 lines, no PII fields). Invalid output twice → `failed`. Cost-cap and provider errors propagate to the caller.
- **Derived in code, not asked from the model:** `type`, `kind` and `platform` from the number format (FBADS/10 digits/BDUE, FBCN/GCN/BDCN for credit notes, `PREFIX-CLIENT-YYMM` for agency), `client_code` from the agency number or the one prefix all campaign refs agree on, `line_no` from line order, `account_id` without dashes.
- **Confidence:** per field, the minimum of pass/fail checks (1 or 0) and the model's own `model_confidence`, so the model can only lower it. Checks: grounded in the visible text (amounts parsed from every layout format with sign, dates in ISO / `01 Jun 2026` / `June 1, 2026`, strings as normalised substrings, IDs as digit runs); arithmetic in `Decimal` (lines sum to subtotal, VAT = subtotal × rate half-up, total = subtotal + VAT, rate 21%); format (dates parse and are ordered, EUR, known number format, campaign ref `CLIENT-PLATFORM-YYMM` matching the invoice's platform and month, ref in `known_campaign_refs` when given); required fields per document type.
- **Statuses:** `rejected` (guard finding), `failed` (unreadable, too large, invalid answer), `needs_review` (any failed check, an ungrounded value, confidence below `EXTRACTION_CONFIDENCE_THRESHOLD` = 0.80, or the model set `contains_instructions`), `extracted` (all checks pass, every field ≥ threshold). There is no `approved` value; reasons are fixed codes like `grounding:total`, `arithmetic:subtotal`, `content:url:text`.
- `test_extraction_generated.py` renders every generated document in a tmp dir (as `test_masking.py` does) and proves zero findings on every benign invoice and credit note and rejection with zero model calls for every inbox copy.
**Consequences:** the vendor number formats are the generator's; real vendors need entries in `NUMBER_FORMATS`. A credit line on an agency invoice prints no campaign ref, so extraction returns null where the ground truth has one (an accuracy gap for 2.6, not a confidence one). Residual risks: hidden text in annotations, form fields or XMP, text the same colour as a coloured box, clipping, text under an image, horizontal scaling and alpha set inside a form's own resources are not detected; the phrase lists miss new wording, homoglyphs and hyphenated breaks. Grounding (T3) and the absence of tools and approvals (T4) are the backstop. 
Not covered either: instructions in another language (the phrase lists are English), near-white text (the colour threshold is 0.98), and any time limit per PDF beyond the 5 MB size cap (T5).

## 043 — Extraction eval: own results file, answer-key malicious list, resumable throttled runs
**Context:** task 2.6 (threat model T3, T5, T7). The quality of `extract_invoice` (042) has to be measured on the generated PDFs, and the measuring must not be able to steer extraction. The eval calls a paid model on a free-tier key (040), so a full run can hit the per-run cap (€0.20) or provider rate limits partway through. `make eval-stage1` rewrites `docs/eval-results.md` as a whole (033), and the demo image ships that file (036).
**Decision:**
- `evals/extraction.py` (`make eval-extraction`, owner-run, never in tests or CI) runs `extract_invoice` on every PDF under `invoices/`, `credit_notes/` and `inbox/`. The extractor gets only the PDF bytes and no known campaign refs, so the document is measured on its own. The harness reads the ground-truth `.json` next to each PDF and compares. `evals/extraction_scoring.py` holds the pure scoring.
- **Malicious list:** the #10 rows of `eval.answer_key`, read as `eval_runner` (033). They must be exactly the ground-truth numbers in `inbox/`, and no #10 number may be outside it; otherwise exit 2 with counts only. So a misfiled copy cannot be silently scored as benign, and the extractor still never sees a path (037).
- **Comparison:** exact `Decimal` and exact strings, on the generator's ground-truth fields per document type. Per field the outcome is correct, wrong (a different value) or null (no value). A `failed` or `rejected` benign document counts as null on every field. Lines match as a multiset on (campaign_ref, description, amount); precision and recall come from that.
- **Known gap**, reported and not hidden: a credit line on an agency invoice extracted with a null ref where the ground truth has one (042) is a line miss in the strict numbers and is also counted on its own row.
- **Dangerous counts:** documents marked `extracted` that differ from the truth, and wrong values whose field confidence reached the threshold. A field no check looked at carries the model's own score (the highest field confidence). Both are reported, not gated.
- **Gate:** exit 1 if any malicious copy is not `rejected` or caused a model call, also on a partial run (malicious copies run first and cost nothing). Accuracy is not gated until stage 5.
- **Cost and rate limits:** the client's caps and retries (039) are unchanged. A `ThrottledCounter` wraps the provider: calls are at least `--min-interval` seconds apart (default 4.5, about 13 per minute) and are counted per document. `--max-cost` can only lower the run cap. Eval runs are not in `app.pipeline_runs`, so the monthly cap counts `monthly_spend` plus the eval's own spend this month from the state file. `CostCapExceeded`, or a `ProviderError` after retries, stops the run with exit 3.
- **Resume:** every scored document is appended to `data/eval/extraction_state.jsonl` (gitignored) with its sha256, status, reason codes, outcome per field, line counts and usage. It never holds values or text. A rerun skips documents whose bytes are unchanged. A different model, prompt hash, data seed or threshold discards the scores but keeps the spend. `--fresh` starts over.
- **Output:** `docs/eval-results-extraction.md`, a file of its own so that `make eval-stage1` and the demo parser are unaffected. It holds counts only, with no numbers, paths or values, and is written only by a complete full run. `--limit N` (first N benign documents plus all malicious copies) and partial runs only print. The terminal lists documents with problems: path, status, reason codes and field names, never values.
**Consequences:** the eval needs the stack up and `make eval-load-key`, like stage 1. A full run takes at least about 10 minutes because of the throttle. The state file can be deleted at any time and only costs a rerun. Task 2.6's "a section in `docs/eval-results.md`" is a separate file instead; joining the two would need a change to the stage-1 eval.
